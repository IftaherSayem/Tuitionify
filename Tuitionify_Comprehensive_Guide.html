1 Project Overview

Tuitionify is a full-stack web application that serves as a tuition marketplace built for the International Islamic University Chittagong (IIUC) community and the Bangladeshi education system. It connects two groups of users:

  • Tutors — university students who offer private tutoring
  • Seekers (guardians / students) — parents or students looking to hire a tutor

Core Value Proposition

Tuitionify removes the friction of finding a tutor in Bangladesh with a trusted, verified, filterable directory — privacy-aware contact sharing, earned reviews, and a structured application flow, all shaped around the local context: BDT salaries, the BD class system (Class 1–12, SSC, HSC, Admission), Chittagong thanas, and the plain fact that hiring here ends on a phone call.

2 System Architecture

Tuitionify is a client-server application: a React single-page app talks to a Node/Express REST API, with MongoDB Atlas for persistence and Firebase for identity. The client and the API deploy as two separate Vercel projects from one repository.

+---------------------------------------------------------------+ | CLIENT (React SPA) | | Vite . React 18 . React Router . Tailwind CSS | | Firebase Auth SDK -- issues + refreshes the ID token | | Axios interceptor -- attaches Bearer token to every call | +------------------------------+--------------------------------+ | HTTPS / JSON REST (Bearer ID token) | +------------------------------v--------------------------------+ | SERVER (Express API) | | | | CORS -> body limits -> rate limit -> DB connect | | | | | verifyToken -> loadUser -> requireRole / requireVerifiedEmail | | | | | 10 route modules . 8 Mongoose models . central error handler | +---------------+-------------------------------+---------------+ | | +--------v---------+ +----------v-----------+ | MongoDB Atlas | | Firebase Admin SDK | | (Mongoose ODM) | | verifies ID tokens | +------------------+ +----------------------+ | +--------v---------+ | imgbb (proxied) | server-side key, never in the bundle +------------------+

2.1 Request Flow

React page→ Axios + token→ Express middleware→ Route handler→ Mongoose→ MongoDB Atlas

Every request passes the same gauntlet before a handler ever runs. The order is deliberate and is defined in server/index.js:

  1. CORS — origin restricted to CLIENT_URL. If that variable is unset in production the server logs a warning at boot, because the fallback is *.
  2. Body parsing with split limits — /api/uploads accepts 4.5 MB (base64 photos need it); every other route is capped at 100 KB so one request cannot tie up memory.
  3. Global rate limit — 200 requests/minute as a backstop; individual write routes set tighter limits.
  4. Database connection — a cached, serverless-safe connect that runs before any handler.
  5. Route handler — with its own auth and rate-limit chain.
  6. Central error handler — converts Mongoose CastError to 400 "Invalid id", names the offending fields on a ValidationError, maps oversized bodies to 413, and hides internal messages on 500s in production.

2.2 Why the client and API are separate deployments

This has one consequence worth stating plainly, because it shapes the code:

The option lists are deliberately duplicated

Subjects, class levels and areas live in both client/src/data/options.js and server/utils/options.js. They are not shared by import, because the two Vercel projects have separate root directories and no common build step — a cross-directory import resolves on a laptop and fails in production.

If you edit one, edit the other, or the API will reject values the UI happily offers. Both files carry this warning in a comment.

A note on password storage

Tuitionify never stores or even sees a password. Firebase owns the credential; the server only ever receives a signed ID token and asks the Firebase Admin SDK to verify it. That removes an entire class of vulnerability — there is no password hash in this database to leak.

4 The System End to End — Two Complete Journeys

The sections after this one describe features individually. This one follows the system as it is actually used, in order, from an empty database to a completed hire and an earned review. Every step names the file and endpoint that does the work, so the guide can be read alongside the code.

4.1 Journey A — Kamal, a guardian, hires a tutor

Step 1 — Sign up and choose a role

Kamal opens /register and signs up with email and password, or with Google. Firebase creates the credential client-side and returns a user object with a UID.

  • Client: Register.jsx calls signupEmail() from AuthContext, which calls Firebase's createUserWithEmailAndPassword, sets the display name, and sends a verification email.
  • Client: he picks the Seeker role and submits, which calls POST /api/users/register.
  • Server: routes/users.js reads uid, email and email_verified from the verified token, never from the request body. The role is validated against ['tutor','seeker']. A Mongo profile is created.

Why email comes from the token, not the body

Admin access is granted by matching user.email against the ADMIN_EMAILS environment variable. If the client could supply its own email at registration, anyone could claim an admin address and self-promote. Taking it from the signed token closes that path, and email is deliberately absent from the editable-fields list on PUT /api/users/me so it cannot be changed afterwards either.

Step 2 — Post a tuition

Kamal fills the form at /post-tuition: title, class level, subjects, area, monthly salary in BDT, days per week, mode, and gender preference.

  • Client: PostTuition.jsx builds the payload from the shared option lists, so every dropdown value is legal by construction. Text inputs carry maxLength matching the server caps.
  • Server: POST /api/tuitions runs requireRole('seeker'), then copies only the nine whitelisted fields from the body. status, createdBy and the timestamps are set by the server, so a crafted request cannot pre-set them.
  • Model: Tuition validates classLevel and area against enums, checks every subject is a real option, and bounds salary to ৳500–100,000 and daysPerWeek to 1–7.
  • Limit: 10 posts per minute.

Step 3 — Tutors apply; Kamal reviews the applicants

  • Kamal opens /dashboard. GET /api/tuitions/mine/posted lists his posts; GET /api/tuitions/:id/applications lists the applicants for one.
  • Ownership is re-checked server-side on that endpoint — the tuition's createdBy must equal the caller. Passing someone else's tuition id returns 403.
  • Unseen applications are stamped viewedAt in a single updateMany, which drives the tutor's timeline later.
  • Applicant phone numbers are stripped from the response unless that application is already accepted.

Step 4 — Accept one

  • PATCH /api/applications/:id with { status: 'accepted' }. The server verifies Kamal owns the parent tuition, stamps decidedAt, and closes the tuition automatically so it stops appearing in listings.
  • The accepted tutor's phone now appears in Kamal's applicant list. He calls them. This is the moment the whole product exists for — and it is why a tutor cannot apply without a valid number.

Step 5 — Review the tutor afterwards

  • On the tutor's profile Kamal sees a review form, because GET /api/users/tutors/:id returned canReview: true for him.
  • POST /api/reviews re-checks that on the server via hasEngagement(), requires a confirmed email, validates the 1–5 rating, and recomputes the tutor's ratingAvg / ratingCount aggregates.
  • A unique index on {tutor, author} means one review per person per tutor; a second attempt returns 409.

4.2 Journey B — Tanvir, a CSE student, gets hired

Step 1 — Register as a tutor and complete the profile

  • Same signup, role Tutor. Tutor-specific fields may be sent at registration, but only from a whitelist — isVerified, restricted and ratingAvg are not in it.
  • At /dashboard?edit=1, TutorProfileForm.jsx collects university, department, subjects, class levels, preferred areas, expected salary, mode, bio and photo.
  • The dashboard nudges him twice: once if subjects or areas are empty (he would be unfindable), and once if his phone is missing (he could not apply). Both are plain amber notices, not blockers.

Step 2 — Upload a profile photo

  • PhotoUpload.jsx checks the MIME type and the 3 MB cap client-side, converts the file to base64, and posts it to POST /api/uploads/photo.
  • The server proxies it to imgbb using a server-side key. The key is never in a VITE_* variable, because anything with that prefix is inlined into the public JavaScript bundle and can be read by anyone.
  • The server re-checks the decoded size, distinguishes a revoked key (503) from a rejected file (502) from an upstream rate limit (429), and logs the real upstream reason either way.
  • Only the returned display_url is stored, and the photo field validates that it is an http(s) URL — so javascript: and data: values cannot be persisted.

Step 3 — Find work

  • GET /api/tuitions with filters, or GET /api/tuitions/recommended, which scores open tuitions against his own subjects (+2), preferred areas (+1) and class levels (+1) and returns the top six.

Step 4 — Apply

  • POST /api/applications. The chain is verifyToken → loadUser → requireRole('tutor') → rate limit, then two checks: his phone must be a valid BD mobile, and the tuition must still be open.
  • A unique index on {tuition, tutor} prevents double-applying; the duplicate-key error is translated to a friendly 409.
  • Limit: 30 applications per hour.

Step 5 — Track it, or withdraw

  • GET /api/applications/mine feeds a four-stage timeline: Applied → Viewed → Decision → Outcome, using createdAt, viewedAt and decidedAt.
  • While an application is still pending he can withdraw it: DELETE /api/applications/:id. Once a decision has been made the endpoint refuses with a 400 explaining why — the outcome is part of the guardian's record and the tuition may already be closed against it.

Step 6 — Handle a contact request

  • A guardian who has not hired him may still ask for his number. GET /api/contact-requests/incoming lists those; PATCH /api/contact-requests/:id approves or declines.
  • Approving is what releases his phone and email to that one seeker — nobody else.

The invariant behind both journeys

Every privacy and trust decision is enforced on the server, by deleting fields from the response — never by hiding them in the UI. The client's own checks exist to keep the interface honest; they are not the security boundary. A user reading the raw API responses sees exactly what a user reading the rendered page sees.

5 Features & How They Work

5.1 Authentication System

Firebase Authentication handles identity; the server verifies tokens with the Firebase Admin SDK and keeps its own user profile keyed by firebaseUid.

Flows supported: email/password signup with verification, Google sign-in (one-tap popup), password reset by email, and email-verification resend.

How a request is authenticated: the Axios interceptor in api/client.js calls auth.currentUser.getIdToken() before every request and sets the Authorization: Bearer header. Firebase refreshes the token transparently when it nears expiry, so a long session never breaks.

5.2 Two-Role System

One User collection serves both roles, with tutor-only fields left empty for seekers. The role is chosen at signup, validated server-side, and drives route access, dashboard layout, and which actions the API will accept.

5.3 Tuition Posting & Application Flow

Seekers post; tutors apply; seekers accept or reject. Accepting closes the tuition. Tutors may withdraw while pending. Covered step by step in §4.

5.4 Advanced Filtering

Both directories filter on subject (multi-select), class level, area, salary range, mode and gender preference; tutors additionally on minimum rating and verified status. Every value is coerced through utils/sanitize.js before it reaches Mongo.

Free-text search runs over a small set of fields with a regex that is escaped and length-capped — see §11.

5.5 Privacy-Gated Contact System

A tutor's phone and email are never in a public listing. A seeker requests contact; the tutor approves or declines; only an approved request reveals the details, and only to that seeker.

Implementation: PRIVATE_FIELDS = '-phone -email' on list queries, and a publicTutor() helper that deletes both fields unless the viewer is the tutor themselves or a seeker with an approved request. The response also carries contactVisible so the UI knows which state to render.

5.6 Review & Rating System

Seekers rate tutors 1–5 with an optional comment; tutors may reply once per review. Aggregates are denormalised onto the user document for fast sorting.

Reviews must be earned — see §6.1, which is the single most important rule in the system.

5.7 Reporting & Trust/Safety

Any confirmed-email user can report a profile or a tuition with a reason and optional details. Reports land in the admin queue as open and move to reviewed or dismissed. Limit: 10 per hour.

5.8 Admin Panel

Admins are identified by email against ADMIN_EMAILS. They can grant or revoke the verified badge, restrict or unrestrict any user, work the report queue, and read the analytics dashboard. All admin routes sit behind verifyToken → loadUser → requireAdmin applied at the router level, so no individual route can forget it.

5.9 Email Verification & Password Recovery

Verification mail is sent at signup and can be resent from a dashboard banner. /auth/action handles Firebase's callback for both verification and password reset in one page. The server syncs emailVerified from the token on every GET /api/users/me.

5.10 Responsive UI & Design System

Mobile-first Tailwind with a custom brand palette, shared utility classes (card, input, btn-primary, chip, badge), skeleton loaders, empty states with a suggested next action, and toast notifications for every mutation.

5.11 Dark Mode

ThemeContext stores the choice in localStorage and toggles a dark class on <html>; Tailwind's class strategy does the rest. Every surface has a dark variant.

5.12 Pagination

Public listings default to 12 per page and cap at 50. Admin tables default to 25 and cap at 100. All paginated endpoints return the same envelope:

{ "data": [ ... ], "page": 1, "totalPages": 4, "total": 43 }

5.13 Search

Tuitions search across title, description and subjects; tutors across name, university, department and subjects. Terms are regex-escaped and capped at 80 characters.

5.14 Bookmarks — Tuitions and Tutors

Two parallel models with the same shape. Both toggle on POST, both have a unique compound index, and both expose a /check endpoint so a listing page can mark saved items in one round trip.

5.15 Profile Photo Upload

Proxied through the API to keep the imgbb key server-side. Covered in §4.2.

5.16 Edit / Delete Tuitions

Owners may edit any of the nine content fields, or delete. Deletion cascades — applications, bookmarks and reports for that tuition are removed in one Promise.all before the document itself, so no orphan rows remain.

5.17 Analytics Dashboard

Fourteen aggregations in a single Promise.all: user/tuition/application counts by state, signups and posts per week over eight weeks, and the top ten subjects and areas. Rendered with Recharts on a lazy-loaded page.

5.18 Tuition Recommendations

Scored against the tutor's own profile: subject match +2, area +1, class level +1. Top six returned. Returns an empty array rather than an error for a tutor who has not filled in a profile yet.

5.19 Application Tracking Timeline

Applied → Viewed → Decision → Outcome, driven by createdAt, viewedAt and decidedAt. The "Viewed" stamp is set when the guardian opens the applicant list, which is honest about what it means: seen, not judged.

5.20 Guardian Management & User Restriction

Admins can restrict any user. A restricted account is refused on every authenticated route and is treated as anonymous on public ones, so a ban is not partially escapable.

5.21 Application Withdrawal

A tutor can withdraw a pending application. Accepted or rejected ones cannot be withdrawn — that outcome belongs to the guardian's record.

6 Trust & Safety Rules

These are the rules that make the marketplace worth trusting. Each is enforced in the API, and each is covered by the test suite.

6.1 A review must be earned

The rule

A seeker may review a tutor only if one of these is true:

  1. the tutor was accepted on one of that seeker's own tuitions, or
  2. the tutor approved that seeker's contact request.

Both require an affirmative act by the tutor. Neither can be manufactured by the seeker alone.

Why it matters. ratingAvg is the primary sort key of the public tutor directory. Without this rule, signup is free and unlimited, so anyone could create throwaway accounts and move a competitor down the listings or their own profile up. The unique index only stops one account from reviewing twice; it does nothing against ten accounts.

Where it lives. server/utils/engagement.js, called from two places:

  • POST /api/reviews — enforcement. Returns 403 with an explanation if it fails.
  • GET /api/users/tutors/:id — returns canReview so the UI can show the reason instead of a form that would be rejected on submit.
// The two proofs, both requiring a tutor-side action.
const myTuitionIds = await Tuition.find({ createdBy: seekerId }).distinct('_id');

if (myTuitionIds.length) {
  const accepted = await Application.exists({
    tutor: tutorId,
    tuition: { $in: myTuitionIds },   // scoped to the seeker's OWN posts
    status: 'accepted',
  });
  if (accepted) return true;
}

return Boolean(await ContactRequest.exists({
  tutor: tutorId, seeker: seekerId, status: 'approved',
}));

This rule is retroactive

Reviews written before it existed remain visible. Some of their authors could not post them today. If the data matters for a demo, it is worth a look.

6.2 Reviews and reports require a confirmed email

Both actions run through requireVerifiedEmail. This is what makes §6.1 expensive to work around at scale: a throwaway account now costs a real, reachable mailbox.

The middleware trusts the live token first and falls back to the stored mirror, so a user who has just clicked the verification link is not rejected by a stale database field.

Posting a tuition and applying are deliberately not gated this way — that would add friction to the core marketplace loop for little gain, since those actions are already role-limited and rate-limited.

6.3 Applying requires a real Bangladeshi mobile number

Hiring here ends on a phone call. A guardian who accepts a tutor with no number has hired nobody, and that dead application clutters their list.

utils/phone.js validates 01 + operator digit 3–9 + 8 digits, and a Mongoose setter normalises the spellings people actually type:

6.4 A ban applies everywhere

loadUser refuses restricted users with a 403. optionalAuth — used by the public tutor and tuition detail pages — loads the same user but does not attach it if restricted, so a banned seeker is treated as an anonymous visitor and loses any contact access an earlier approval had granted.

6.5 Contact details are removed, not hidden

Every path that could expose a phone or email deletes the field server-side before responding: tutor listings, tutor detail, tuition detail (poster's phone), applicant lists (until accepted), and the seeker's own contact-request list (until approved).

6.6 Server-controlled fields are never taken from the body

Every write route copies from an explicit whitelist. isVerified, restricted, ratingAvg, ratingCount, emailVerified, status, createdBy and all timestamps are set by the server or an admin, and appear in no whitelist.

9 Authentication & Authorization

9.1 The full authentication flow

Firebase login→ ID token→ Axios attaches→ Admin SDK verifies→ Load Mongo user→ Guards
  1. The user signs in; Firebase issues a signed JWT holding uid, email and email_verified.
  2. onAuthStateChanged in AuthContext fires, and the app fetches GET /api/users/me for the Mongo profile that carries the role.
  3. Every subsequent request goes through the Axios interceptor, which calls getIdToken() — refreshing transparently if needed — and sets the Bearer header.
  4. The server verifies the signature with the Firebase Admin SDK. A forged or expired token fails here with a 401.

9.2 The middleware chain

MiddlewareResponsibilityFailure
verifyTokenVerify the Bearer token, attach req.firebaseUser401
loadUserLoad the Mongo profile into req.dbUser; reject restricted accounts404 / 403
optionalAuthAttach the user if a valid token is present; skip restricted users; never reject—
requireRole(r)Require tutor or seeker403
requireVerifiedEmailRequire a confirmed address; live token first, stored mirror as fallback403
requireAdminMatch the user's email against ADMIN_EMAILS, case-insensitively403

Typical composition, from the review route:

router.post('/',
  verifyToken,             // is this a real, current token?
  loadUser,                // who are they, and are they banned?
  requireRole('seeker'),   // only guardians review tutors
  requireVerifiedEmail,    // a throwaway account should cost a mailbox
  rateLimit({ windowMs: 3_600_000, max: 15, name: 'review' }),
  handler,                 // ...which then checks hasEngagement()
);

9.3 Client-side route protection

ProtectedRoute handles four states: still loading (spinner), signed in without a profile (redirect to /complete-profile), signed out (redirect to /login carrying the intended destination), and wrong role or non-admin (redirect to /dashboard).

The client guard is convenience, not security

ProtectedRoute stops a user wandering into a page that will not work for them. It is not what protects the data — every one of those routes is independently enforced server-side. Disabling the client check in a browser console reveals nothing: the API still answers 401 or 403.

11 Security Analysis & Report

11.1 What the project does well

  • No password ever touches this system. Firebase owns credentials; there is no hash in this database to leak.
  • Mass assignment is closed everywhere. Every write copies from an explicit whitelist, so isVerified, restricted, ratingAvg, status and createdBy cannot be set by a crafted body.
  • Identity comes from the token. Email is read from the verified JWT and is not editable, which is what keeps ADMIN_EMAILS meaningful.
  • NoSQL injection is systematically handled. utils/sanitize.js coerces every query value to a scalar, so ?area[$ne]=x becomes an empty string instead of a Mongo operator.
  • Regex search is escaped and capped, closing both a 500-on-( crash and a ReDoS vector.
  • Ownership is re-checked on every mutating route, never inferred from the client.
  • PII is deleted server-side rather than hidden in the UI.
  • The imgbb key stays on the server. A VITE_* variable would have been inlined into the public bundle.
  • Errors do not leak internals — CastError and ValidationError are translated, and 500 text is suppressed in production.
  • CSRF is structurally absent. Auth rides in an Authorization header, not a cookie, so a third-party page cannot make an authenticated request on the user's behalf.

11.2 Findings from the security review, and their resolution

A full review was carried out across the API, the models and the client. Findings and outcomes:

11.3 Two findings assessed and deliberately not "fixed"

The admin query filter was never exploitable

It was reported first as a high-severity injection. On inspection it sits behind requireAdmin, and an admin can already list every report by omitting the filter — there is no privilege boundary to cross. It was corrected for consistency with the sanitizer discipline used everywhere else, not because it was a hole.

The uuid advisory is not reachable

npm audit reports a bounds-check issue in uuid, reached through firebase-admin. It only triggers when a buf argument is supplied, which firebase-admin never does. Fixing it requires a breaking major upgrade for no security gain, so it is knowingly left in place.

11.4 Known, accepted limitations

A ban does not survive a new signup

restricted is a flag on a Mongo document, not on a person. A banned user can register a fresh email and return as a new account. This cannot be closed in application code — the address must also be disabled in the Firebase console. It is the one gap the review could not resolve.

Rate limits are per-instance

The limiter holds counters in memory, so on Vercel each serverless instance counts separately. It stops a single client hammering an endpoint; it is not a strict global limit. A shared store such as Redis would be required for that.

Admin actions are not audited

Restricting a user or dismissing a report leaves no record of who acted or when. With several addresses in ADMIN_EMAILS this is a real gap for a trust-and-safety surface, and it is the first thing worth building next.

11.5 Overall assessment

The security model is sound and, importantly, defence-in-depth rather than perimeter-only: the client hides what a user should not act on, the API refuses what a user may not do, and the schema refuses what should never be stored. Each layer holds on its own.

The highest-value fix was not a classic vulnerability at all — it was the review-engagement rule. No attacker tooling is needed to farm ratings with free accounts, and ratings are what the entire directory ranks on. That is the kind of flaw that matters most in a marketplace, and it is now closed and covered by tests.

12.1 The suite was checked against deliberate regressions

A passing test proves nothing unless it can fail. Both critical protections were removed on purpose to confirm the suite notices:

Protection removedResult
The restricted check in optionalAuth1 test failed, naming the exact behaviour
Both status filters in hasEngagement2 tests failed — the pending and unapproved cases

The source was restored and the suite returned to green. The engagement rule and the phone gate were additionally verified end-to-end against a live MongoDB: a stranger cannot review, a seeker who merely posted a tuition cannot, a pending application does not unlock it, an accepted one does and only for that seeker, and off-list subjects and malformed phones are rejected on save rather than merely in validation.

What is not covered

There are no HTTP-level route tests and no frontend tests. The suite deliberately targets the logic where a silent regression would do real damage — authorization and validation — rather than chasing a coverage percentage. Route-level tests with supertest and an in-memory MongoDB are the natural next step.

13 Deployment Guide

13.1 Architecture

One repository, two Vercel projects. The client builds as a static Vite site; the API runs as a serverless function. They are deployed separately and point at each other by URL.

GitHub repo (one) | +-- Vercel project #1 -- root: client/ -- Vite --> tuitionify.vercel.app | +-- Vercel project #2 -- root: server/ -- Node --> tuitionify-api.vercel.app | MongoDB Atlas <--+--> Firebase Admin

13.2 API deployment

  1. Import the repository into Vercel; set Root Directory to server and the framework preset to Other.
  2. Add every variable from server/.env. Paste FIREBASE_PRIVATE_KEY with its \n sequences intact — config/firebase.js converts them back to real newlines.
  3. Deploy, then confirm /api/health returns { ok: true }.
  4. Once the client is live, set CLIENT_URL to its URL and redeploy so CORS narrows from the * fallback.
VariablePurpose
MONGODB_URIAtlas connection string
FIREBASE_PROJECT_IDFrom the service-account JSON
FIREBASE_CLIENT_EMAILFrom the service-account JSON
FIREBASE_PRIVATE_KEYFrom the service-account JSON, \n preserved
ADMIN_EMAILSComma-separated admin addresses
IMGBB_API_KEYImage host key — server-side only
CLIENT_URLCORS origin; falls back to * with a warning if unset

13.3 Client deployment

  1. Import the same repository again; set Root Directory to client, preset Vite.
  2. Add the six VITE_FIREBASE_* values plus VITE_API_URL pointing at <your-api-url>/api.
  3. client/vercel.json already rewrites all paths to index.html so client-side routing survives a page refresh.

What belongs in a VITE_* variable — and what never does

Anything prefixed VITE_ is compiled into the public JavaScript bundle and is readable by any visitor. The Firebase web config belongs there: it is public by design, and Firebase security rules plus authorised domains are what actually protect the project. The imgbb key does not belong there, which is exactly why uploads are proxied through the API.

13.4 Firebase configuration

  1. Authentication → enable Email/Password and Google.
  2. Project settings → register a Web app and copy the config into the client variables.
  3. Service accounts → generate a private key for the three server variables.
  4. Add the deployed client domain under Authentication → Settings → Authorized domains, or Google sign-in fails in production while working locally.

13.5 MongoDB Atlas

  1. Create a free cluster and a database user.
  2. Network Access: allow 0.0.0.0/0, since Vercel's serverless IPs are not fixed.
  3. Copy the driver connection string into MONGODB_URI.

The connection is cached across invocations in config/db.js, and the cache is cleared on failure so a transient outage does not poison every later request.

14 Known Limitations & Roadmap

14.1 Highest value next

ItemWhy it matters
Admin audit logRestrictions and report decisions currently leave no record of who acted. With multiple admins this is the clearest remaining trust-and-safety gap.
Route-level testsThe suite covers logic thoroughly but never exercises a real HTTP request. supertest with an in-memory MongoDB would close that.
Firebase-side bansPair a restriction with disabling the Firebase account, so a ban survives a re-signup.
Shared-store rate limitingRedis or Upstash would make limits global rather than per-instance.

14.2 Product features not yet built

  • In-app messaging — deliberately out of scope; the contact-request flow substitutes for it, and the schema leaves room.
  • Notifications — email or in-app alerts when an application is decided or a contact request arrives.
  • Tutor availability calendar — days and time slots, so a guardian can match a schedule before applying.
  • Multi-city support — the area list is Chittagong-only today; a city dimension would generalise it.
  • Saved searches — store a filter set and alert on new matches.
  • Tuition expiry — auto-close stale posts so the listing stays current.

14.3 Engineering improvements

  • Remove the options duplication — a shared workspace package would let both halves import one list, replacing the sync warning in §2.2.
  • Compound indexes — the listing sorts (status + createdAt, isVerified + ratingAvg + createdAt) are unindexed and sort in memory. Irrelevant at current scale, worth adding before it is not.
  • Schema validation at the edge — Zod or Joi on request bodies would move validation ahead of Mongoose and yield more precise errors.
  • TypeScript — would have caught the response-shape change that pagination introduced, at compile time rather than by inspection.
  • Error boundaries — a render error currently blanks the page rather than degrading gracefully.

Closing note

Tuitionify is a complete, working marketplace: two roles, a full hiring loop from post to applicant to accepted tutor to earned review, privacy-gated contact sharing, an admin trust-and-safety surface, and a test suite over the rules that matter. The parts that remain open are documented above rather than left to be discovered — including the one gap, ban evasion by re-signup, that application code alone cannot close.
